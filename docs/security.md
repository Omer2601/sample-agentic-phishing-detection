# Security

This page lists the security controls the sample deploys and what stays your job. For threats and residual risks, see [threat-model.md](threat-model.md).

## Shared responsibility

- AWS secures the services this sample runs on. You secure what you deploy with it: who can sign up, who can call the API, your data, and your account.
- This is sample code, not production ready. Review it, run your own security testing, and add what your organization requires (custom domain and TLS policy, separate accounts per stage, backups) before real use.

## Authentication and authorization

| Route                                                                                   | Auth                          | Who can call it                               |
| --------------------------------------------------------------------------------------- | ----------------------------- | --------------------------------------------- |
| Web app pages and `/api/*`                                                              | Amazon Cognito session cookie | Signed-in users; the web tier signs each call |
| `GET /auth/config`, `POST /auth/register`, sign-in pages                                | None                          | Anyone, so they can register and sign in      |
| `POST /scan`, `GET /scans/lookup`, `GET /scans/{id}`, `POST /scans/{id}/retry`          | IAM (SigV4)                   | Principals allowed `execute-api:Invoke`       |
| `POST /batches`, `GET /batches`, `GET /batches/{id}`, `POST /batches/{id}/retry-failed` | IAM (SigV4)                   | Same                                          |
| `GET /history`, `GET /stats`, `GET /stats/export`, `GET /feed/phishing`                 | IAM (SigV4)                   | Same                                          |
| `GET /health`                                                                           | None                          | Anyone. Returns `{"ok": true}` only           |

- **Sign-up.** By default (`signUpMode=app`) the user pool allows admin-created users only. The Register route takes an email, calls `AdminCreateUser`, and Cognito emails a temporary password; the first sign-in proves inbox ownership and forces a new password. The web tier never sets or sees a password. The response is identical whether or not the account exists. With `signUpMode=cognito` the pool uses Cognito self sign-up with email verification.
- **Who may register.** Optional invite code (`-c inviteCode=true`, stored in AWS Secrets Manager) and optional email domain allowlist (`-c allowedEmailDomains=...`).
- **Email delivery.** Cognito's default email sender allows 50 emails per day per account. For real use, deploy with `-c sesFromAddress=<address>`, an address verified in Amazon SES in your Region (and out of the SES sandbox).
- **MFA.** TOTP only, never SMS. Optional by default (`-c mfa=optional`): the first sign-in offers an authenticator. Deploy with `-c mfa=required` to force enrolment. `-c cognitoPlan=plus` adds Cognito threat protection (compromised credentials, adaptive authentication) in enforced mode, billed per monthly active user.
- **Register rate limit.** AWS WAF blocks more than 10 `POST /auth/register` requests per 5 minutes per IP with `429` and `{"error":"too_many_registrations"}`, which protects the Cognito email quota. Behind it the web tier allows 5 registrations per client IP per 15 minutes in each running function instance, also answered with `429`.
- **API resource policy.** It allows only `GET /health` to anyone (over TLS). Every other method is IAM-authorized: a principal in your account is let in by its own identity policy (the web tier role or a holder of the `ApiInvokePolicy` output), and a principal in another account would also need an Allow in this resource policy, which no other method has, so other accounts cannot call the API.
- **Owner isolation.** Every read checks that the scan or batch belongs to the caller and returns `404` otherwise. Access is denied by default. `Idempotency-Key` claims, `GET /scans/lookup` and `POST /scan` deduplication use the same owner key (each web console user, or each IAM identity calling directly), so no caller can replay, look up or be handed another caller's scan.

## Data protection

- AWS KMS customer managed key on DynamoDB tables, S3 buckets, SQS queues and CloudWatch log groups.
- TLS only: bucket policies deny non-TLS requests; CloudFront redirects HTTP to HTTPS. With a custom domain (`-c domainName`, `-c certificateArn`) the distribution requires TLS 1.2 (`TLSv1.2_2021`); the default `*.cloudfront.net` certificate cannot pin a minimum version.
- S3 Block Public Access on every bucket. The web bucket is read by CloudFront through origin access control only.
- Model prose (summary, disagreements, missed points, report) is defanged by the worker before it is stored, so no stored report holds a clickable phishing link; the scan's `url` field stays exact for API consumers. HTML reports (`GET /scans/{id}/report`, `GET /batches/{id}/report`) escape every value, defang every URL (in signal evidence and model prose too) and carry a Content-Security-Policy that allows only their own inline stylesheet. The API checks the owner before it writes or signs anything, and the presigned link forces a download (`Content-Disposition: attachment`) and expires after 15 minutes.
- Retention: scans and batches `retentionDays` (default 90), artifacts 30 days, uploads 1 day. See [architecture.md](architecture.md#where-data-lives).

## Network

- **Edge.** CloudFront with AWS WAF managed rule groups (Common, Known Bad Inputs) and a rate limit of 3,000 requests per 5 minutes per IP, which leaves room for a user polling a batch every 2 seconds and Insights every 5 seconds (about 210 requests).
- **Scan routes.** On `/api/scan*` and `/api/batches*` only, the managed `*_BODY` rules run in Count mode. A phishing URL in a request body looks like SSRF, LFI or XSS to those rules, and in the previous version they blocked 14 batch uploads (`SizeRestrictions_BODY`) and one scan (`EC2MetaDataSSRF_BODY`). Compensating controls: IAM auth, URL validation, the SSRF guard, and the input guardrail. Every other route keeps full blocking.
- **API.** API Gateway stage throttling at 50 requests per second, burst 100.
- **Result cache.** An optional DynamoDB table (`phish-cache-<env>`, encrypted with the data CMK, point-in-time recovery on) holds two kinds of public-source lookup results, never scan content or URLs: RDAP registration fields per registered domain (7 days) and web search result titles, URLs and snippets per brand (24 hours). The agents read and write it by key only (`GetItem`, `PutItem`, `UpdateItem`) and treat it as optional: with `PHISH_CACHE_TABLE` unset, or on any error, they fail open to a live lookup. Cache poisoning: a search result is untrusted text, and a cached one would be served to every scan that names the same brand. That is why the search TTL is 24 hours rather than days, why only successful non-empty results are stored (an error or empty answer cannot pin a bad state), why the row is re-fenced as untrusted content and re-marked against each scan's host on every read, and why a poisoned row ages out on its own. Grant the table to the url_analyst, tools and brand_visual runtime roles only. To flush early, delete the row by key.
- **Outbound.** The agents reach the internet only through AgentCore Browser, the HTTP probe and the RDAP lookup, all behind an SSRF guard that resolves each host and refuses it when any address is private, loopback, link-local or metadata (decisions are cached per origin for 60 s). The HTTP probe resolves every hop again without the cache and connects only to the addresses that check approved, keeping the hostname for TLS and the Host header, so a DNS answer that changes after the check (rebinding) is never dialled; AgentCore Browser and the RDAP client resolve names themselves. The HTTP probe runs when the browser cannot answer the pre-check (8 s in total), once per scan in `url_analyst` to read the URL's redirect chain (6 s in total, in process in both modes), and in the tools server when `code_analyst`'s browser capture fails (navigation timeout, browser refusal or browser error; what is left of the 20 s capture budget, about 4 s) to read the final page's raw HTML: GET requests, redirects followed by hand (at most 5), every hop through the same guard, at most 64 KB read as sent on the wire (it asks for `Accept-Encoding: identity` and never decompresses, and a compressed body is not kept, so nothing inflates past the cap); the probe itself never parses or executes the content. For `code_analyst` only a body served as `text/html` or `application/xhtml+xml` is used, and the bytes are split into tags by Python's `html.parser` into a bounded excerpt (forms, input types, form actions, script sources, inline script snippets, external hosts), fenced as untrusted content and labelled "raw HTML, not rendered, scripts not run": no script runs, nothing it links to is fetched, and no excerpt is made from a Cloudflare warning, bot challenge or other block page. After a browser refusal (`blocked_by_browser`) this GET reaches a page the managed browser's own blocklists turned away, the same trade-off the pre-check already makes; it is a read of at most 64 KB, never a render. On a Cloudflare warning page the browser clicks the warning's own same-origin proceed control once, only when it is enabled; it never solves a captcha or bot check, and every hop of that navigation and the final URL go through the same guard. When a capture fails because the certificate does not cover a `www.` name, the browser opens the same host without `www.` once, in the same session and budget; that host is derived from the submitted URL and goes through the same preflight and guard as the first navigation. By default the browser is the AWS-managed `aws.browser.v1`. With `-c browserSigning=true` it is a custom AgentCore Browser that signs its requests with Web Bot Auth, so sites can tell it is a verified bot; it has no permissions of its own and recording is off. AgentCore Web Search queries go to an AWS-owned connector behind an IAM-authorized AgentCore Gateway and stay inside AWS.

## Generative AI controls

- Page content is untrusted. It is wrapped in delimiters, capped in size, and every prompt says it is data, never instructions. Web search results get the same treatment, and a result served by the scanned site is marked so it cannot confirm itself.
- Amazon Bedrock Guardrails check every submitted URL (input) and every report (output). An intervention is recorded on the scan in `guardrail_events` and never drops it. The input guardrail blocks a URL that carries a US Social Security number, a credit or debit card number, an AWS access key ID or an AWS secret access key. The output guardrail masks a US Social Security number, a credit or debit card number or an AWS access key ID in the report text and keeps the rest of the report and the verdict. It does not mask AWS secret access keys: that detector matches any long random-looking string, and it masked the random host names of free-hosting phishing pages, which are the evidence the report cites.
- A model-level block is retried once with sanitized content, then becomes a `blocked_by_guardrail` finding the orchestrator treats as suspicious evidence.
- The verdict is parsed from the last `<verdict>` block, or, when there is none (the compact turn 1 reply), from the last JSON object with a `verdict` key, and validated against a schema.
- Episodic memory (on by default) stores one line per completed scan, written after the output guardrail: the defanged URL, verdict, risk and a reason capped at 160 characters. Lines are flattened (no new lines, no angle brackets) before they reach the orchestrator, under a label that says they are not evidence, so a stored summary cannot forge a `url:` line or a `<verdict>` block. Memory summaries are shared within a deployment as model context: the orchestrator may be shown a summary of another user's scan. A record holds no owner id or email. The result page and `GET /scans/{id}` list as similar past scans only matches whose scan the requester owns (checked against the `scans` table), and never return another owner's scan id. Deploy with `-c episodicMemory=false` if shared model context is not acceptable. The worker can only append records and run a semantic search (`BatchCreateMemoryRecords`, `RetrieveMemoryRecords`) on that one memory.
- The orchestrator harness runs without managed memory, so it keeps no state between scans. The two turns of one scan share one runtime session, and the worker passes `actorId` = the scan id on every `InvokeHarness` call. This closes a cross-user leak: before, every scan used the harness memory actor `default`, and a 2026-10-16 test showed a session quoting scan ids from earlier sessions. The app's own AgentCore Memory (similar past scans, above) is unchanged.
- With `-c agentRegistry=true` (off by default), AWS Agent Registry (part of Amazon Bedrock AgentCore) records are created by the stack and auto-approved. The orchestrator looks them up once through the `registry` target on its one Gateway, `phish-specialists`, and can call tools only on that Gateway, so a tampered record can at most change which of that Gateway's own tools the model picks, never redirect it to another endpoint, and round one is always the dispatcher call. A failed lookup is noted and the scan goes on.
- Capture is passive, with one bounded exception. The tools server does not solve or wait out bot checks, and does not type or submit data into pages, so nothing typed by the sandbox can leave it. The exception: on a Cloudflare "Suspected Phishing" or "Suspected Malware" page it clicks that warning's own same-origin proceed control (`form[action="/cdn-cgi/phish-bypass"]`) once, only when Cloudflare has already enabled it, never touching the Turnstile widget, so the real page can be judged. The click submits Cloudflare's GET form, nothing of the site's.
- A capture gap is not evidence. `blocked_by_browser` (the managed browser refused the URL before sending a request), `bot_challenge`, `tls_error` (a certificate or TLS error: the host answered, so it is never read as a dead site) and `static_html_only` (`code_analyst` read only the raw HTML, so the rendered page was not observed) are `low` signals that lower confidence; the orchestrator prompt says they are never phishing evidence on their own. `capture_note` is written by code, not by a model.
- Model access is scoped to the two inference profiles. No code calls a model outside an agent.

## IAM

One role per component (web tier, API, split, worker, stats, sweeper, each specialist runtime, the dispatcher runtime, the tools runtime, the harness, the specialists Gateway, the tools Gateway, the web search Gateway). Only the tools runtime role holds `StartBrowserSession` and the screenshot and `capture.json` write grants; each specialist writes its own Finding only, `brand_visual` alone can read `screenshot.png` back, and the harness role cannot invoke the tools Gateway. The worker role can call `InvokeAgentRuntime` on the tools runtime and its endpoints for `precheck_url`, and on no specialist or dispatcher runtime. With `directOrchestration` (on by default, off with `-c directOrchestration=false` or `-c agentRegistry=true`) it can also invoke the dispatcher runtime and its endpoints, and the orchestrator model, because it then runs round one and the two orchestrator calls itself; it still cannot invoke a specialist runtime unless `directSpecialists` (on by default, only with direct orchestration) adds the three specialist runtimes and their endpoints, never a tools runtime. With `directTools` (on by default) `brand_visual` and `code_analyst` can each invoke the tools runtime (or, with `splitToolsRuntimes`, also on by default, only their own copy of it) and its endpoints; `url_analyst` gets no tools runtime grant. The specialists Gateway role can invoke the dispatcher and the three specialist Runtimes behind its targets, not the tools runtime, and, only with `-c agentRegistry=true`, serves the `registry` target that searches the stack's Agent Registry (`InvokeRegistryMcp` and `SearchDiscoverableRegistryRecords` on that registry only). The dispatcher role can invoke only the three specialist Runtimes and write only the three `scans/*/findings/<agent>.json` keys; it has no Bedrock, browser, Gateway or cache grant. IAM authorizes the tools Gateway per Gateway, not per tool, so any specialist role could call any tool there (residual risk; the tools validate every URL and scan id). The web search Gateway role may call `bedrock-agentcore:InvokeWebSearch` on the AWS-owned `tool/web-search.v1` ARN only; only the `brand_visual` runtime role may invoke that Gateway. In a Region that offers Web Search that Gateway is regional instead, still separate from the tools Gateway and invocable only by the `brand_visual` runtime role. Wildcards appear only where the service requires them:

| Wildcard                                                | Why                                                              |
| ------------------------------------------------------- | ---------------------------------------------------------------- |
| Region in the Bedrock foundation-model ARNs a profile routes to | Cross-region and global profiles are served from several Regions. The profile ARN itself is in your Region, and the model ARNs are allowed only with `bedrock:InferenceProfileArn` equal to this stack's profile, so no model can be called directly |
| `browser-session/*` in your account                     | Browser session ids are created per scan. The browser itself is named by ARN: `aws.browser.v1` (the default) or the signed custom browser (`-c browserSigning=true`) |
| `runtime-endpoint/*` on the runtimes and the harness (Gateway roles, dispatcher, worker) | `InvokeAgentRuntime` and `StopRuntimeSession` also authorize the endpoint ARN |
| `scans/*`, `uploads/*` in one bucket each               | Object keys contain ids created at runtime                       |
| `/index/*` on each table                                | Queries use the table's own indexes                              |
| `*` for X-Ray `PutTraceSegments`, `PutTelemetryRecords` (and `GetSampling*` on the runtimes), `ecr:GetAuthorizationToken` and `cloudwatch:PutMetricData` on the runtimes, `dynamodb:ListStreams` on the stats aggregator | These actions have no resource-level permissions; `PutMetricData` is limited by a `cloudwatch:namespace` condition |

## Logging and monitoring

- CloudWatch Logs for every Lambda, runtime and the API (structured JSON, no secrets, URLs never logged unvalidated).
- CloudWatch metrics (namespace `PhishTriage`) for scan time, tokens, cost and AgentCore calls. X-Ray tracing on the Lambdas.
- Alarms (10): the scan, stats-stream and CSV-batch dead-letter queues not empty, queue backlog, worker errors, worker throttles, API 4XX and 5XX rates, and API 403 and 401 spikes. They publish to the SNS topic `<appName>-alarms-<env>` (encrypted with the stack key, TLS-only, and only CloudWatch alarms of this stack may publish). Subscribe an email or chat endpoint to it to be notified.
- AWS CloudTrail in your account records every control-plane call. The sample does not create a trail; use your account's trail.

## Supply chain

- Python dependencies are pinned in `uv.lock`, JavaScript dependencies in `web/package-lock.json`.
- Known advisory, not exploitable here: `mcp` 2.1.1 has CVE-2026-59951 (unbounded session accumulation in the StreamableHTTP transport, fixed in 2.2.0). `strands-agents` (latest checked: 1.62.0, 2026-10-27) still requires `mcp<2.2`, so the pin cannot move yet. Every MCP server in this sample (the three specialists, the dispatcher and the tools server) runs with `stateless_http`, which keeps no session store, and is reachable only through IAM-authenticated AgentCore Runtime. A test (`agents/tests/test_server.py::test_every_mcp_server_is_stateless`) fails if any server leaves stateless mode. Move to `mcp>=2.2` when `strands-agents` allows it.
- Security scanners (static analysis, IaC checks with cdk-nag, cfn-lint and checkov, dependency checks) run before each push. See `scripts/prepush.py`.
- CI takes every tool from a pinned image: uv comes from the official `ghcr.io/astral-sh/uv` image (copied into the Node jobs as a job artifact), never from a script download.
- Processes are started from as few places as possible, each with a list argv (never a shell) that starts with a literal program name, and no user input. A variable program name would hide which executables can run, so each launcher has one call per program it allows. Bandit reports each call as B603 (Low); they stay because the programs have no Python API:
  - `scripts/prepush.py` `execute()`: the pre-push gate's only launcher, one call each for git, uv, npx, npm and the gate's scanner CLI. The other gate scripts and the gate tests go through it.
  - `infra/phish_infra/common.py` `run_build_step()`: the CDK app's only launcher, one call each for uv and npm, for asset builds.
  - `scripts/preflight.py` `node_version()`: `node --version`, because the Node.js version is only available from the binary the CDK CLI will run.
  - `agents/tests/test_dockerfile.py`: runs the Dockerfile's own `uv export` line to prove it works from the copied files.
  - `web/server/test_run_sh.py`: runs `web/run.sh` under `/bin/sh` with a stub `python3`, to see the exact gunicorn argv.
