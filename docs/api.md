# API

Everything the web app does, you can do with the API. Requests are signed with AWS Signature Version 4 (IAM auth), so any AWS SDK or `awscurl` works.

## Authentication

The API is authenticated with IAM SigV4 on every route except `GET /health`. Amazon Cognito gates only the web console: it signs users in to the web app, and it plays no part in a direct API call. To call the API yourself you sign each request with AWS credentials that your IAM principal already has, for example the ones your AWS CLI uses.

With the AWS CLI credentials you already have (profile, SSO or environment), `awscurl` signs the request for you:

```bash
export AWS_PROFILE=<your profile>   # skip if you use the default credentials
awscurl --service execute-api --region "$AWS_REGION" "$API/history?limit=5"
```

The Python example below does the same with `boto3` and `SigV4Auth`. An unsigned call, or a signer without `execute-api:Invoke` on the API, gets `403`.

## Scan one URL

```bash
awscurl --service execute-api --region "$AWS_REGION" -X POST "$API/scan" \
  -H 'Content-Type: application/json' -d '{"url": "https://example.com"}'
```

```json
{ "scan_id": "3f2a9c1e-7b4d-4e0a-9d61-0c8e5b2f7a10", "status": "PENDING", "deduplicated": false }
```

The body is `{"url": "..."}` plus an optional `"force": true` (see [Reuse a recent scan](#reuse-a-recent-scan-lookup-and-dedup)); any other field is a `400`. `deduplicated` is always present and is `false` unless deduplication is turned on and handed back an earlier scan. If the scan cannot be queued (the queue send fails twice) the answer is `503 {"error": "the scan could not be queued; try again"}` and the scan is stored as `FAILED` with that reason, so submit again.

Poll until `status` is `COMPLETE` or `FAILED` (every 2 seconds is fine). `COMPLETE` means the verdict is available; the full report may still be written afterwards, see [Verdict first, report second](#verdict-first-report-second):

```bash
awscurl --service execute-api --region "$AWS_REGION" "$API/scans/3f2a9c1e-7b4d-4e0a-9d61-0c8e5b2f7a10"
```

```json
{
  "scan_id": "3f2a9c1e-7b4d-4e0a-9d61-0c8e5b2f7a10",
  "url": "https://example.com",
  "status": "COMPLETE",
  "verdict": {
    "verdict": "legitimate",
    "risk_score": 3,
    "confidence": "high",
    "action": "allow",
    "summary": "A long-established domain with no login form, no brand impersonation and no suspicious scripts.",
    "report_markdown": "**AI-generated analysis: human review required.** ...\n\n---\n\n## Verdict\nLegitimate.\n...\n\n---\n\n**AI-generated analysis: human review required.** This output was generated by AI and can be wrong. A qualified human analyst must review it before any action is taken."
  },
  "report_status": "READY",
  "report_started_at": "2026-10-05T12:00:31Z",
  "report_ready_at": "2026-10-05T12:00:52Z",

  "findings": ["...one Finding per specialist..."],
  "calls": ["...one timing entry per AgentCore call..."],

    }

```

`similar_scans` lists your own earlier scans (episodic memory, up to 3) that the orchestrator saw as context. They are not evidence for this URL. Matches from other users' scans are never listed and their scan ids are never returned. Only this route fills the field; the list is empty when `-c episodicMemory=false` or none of the matches is yours.

The response is trimmed. Field meanings are in [agents/orchestrator.md](agents/orchestrator.md) (`verdict`) and the specialist pages (`findings`).

## Retry safely with an Idempotency-Key

Without a key every `POST /scan` creates a new scan with its own cost, so a retry after a timeout can scan the URL twice. Send an `Idempotency-Key` header (1 to 128 letters, digits, `.`, `_`, `:` or `-`; a fresh UUID per logical submission) and reuse it, with the same body, on every retry of that submission:

```bash
awscurl --service execute-api --region "$AWS_REGION" -X POST "$API/scan" \
  -H 'Content-Type: application/json' -H "Idempotency-Key: $(uuidgen)" \
  -d '{"url": "https://example.com"}'
```

| Request | Answer |
| --- | --- |
| First request with a key | `202` and a new scan, as without a key |
| Same key, same `url` | `200`, header `Idempotent-Replayed: true`, body `{"scan_id", "status", "deduplicated"}` with the original `scan_id` and its current `status`. No new scan, no new cost. `force` does not change this |
| Same key, different `url` | `422 {"error": "Idempotency-Key was already used with a different url"}` |
| Same key while the first request is still being processed | `409`, header `Retry-After: 2` |
| Malformed key | `400` |
| The scan could not be queued | `503`; the key is released, so retry with the same key |

Keys are kept for 24 hours and are scoped to the caller: each web console user, and each IAM identity calling the API directly, has its own keys, so one caller can never replay another caller's scan. With a key, retry `POST /scan` on network errors, `409`, `429` and `5xx`, and honor `Retry-After`. Without a key, retry it on `429` only, and after a `5xx` or a network error check `GET /scans/lookup` or `GET /history` before you submit again.

## Reuse a recent scan: lookup and dedup

`GET /scans/lookup?url=<url>` answers "have I scanned this URL, and with what result?" without starting a scan. It returns your latest scan of the URL, matched after normalising the scheme and host case and a default port (path, query and fragment must match exactly). FAILED scans are skipped unless you add `include_failed=true`. URL-encode the value and sign the exact query string you send:

```bash
awscurl --service execute-api --region "$AWS_REGION" "$API/scans/lookup?url=https%3A%2F%2Fexample.com"
```

```json
{
  "found": true,
  "url": "https://example.com",
  "scan_id": "3f2a9c1e-7b4d-4e0a-9d61-0c8e5b2f7a10",
  "status": "COMPLETE",
  "verdict": "legitimate",
  "risk_score": 3,
  "confidence": "high",
  "completed_at": "2026-10-05T12:00:31Z",
  "queued_at": "2026-10-05T12:00:02Z",
  "age_seconds": 11,
  "disclaimer": "..."
}
```

`verdict`, `risk_score` and `confidence` are `null` until the scan is `COMPLETE`. `age_seconds` counts from `completed_at`, or from `queued_at` while the scan is not complete; decide your own freshness limit. A URL you never scanned gives `{"found": false, "url": "..."}`. A bad `url` or an `include_failed` other than `true`, `false`, `1` or `0` is a `400`.

Deployed with `-c scanDedup=true` (off by default, see [configuration.md](configuration.md)), `POST /scan` from a direct API caller hands back your own `PENDING` or `RUNNING` scan of the same URL, or one that finished `COMPLETE` in the last 24 hours, as `202` with `"deduplicated": true`, instead of scanning again. FAILED scans are never reused, and `"force": true` always starts a new scan. Scans submitted from the web console are never deduplicated, so "scan again" there always runs a fresh scan. Lookup works whether or not dedup is on; scans stored before this version are not found by either.

## Verdict first, report second

A scan returns its verdict first and keeps writing the full report in the background. Two fields describe progress and they are independent:

| Field           | Values                                     | Meaning                                                                                                                                                                                                                                                                |
| --------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `status`        | `PENDING`, `RUNNING`, `COMPLETE`, `FAILED` | `COMPLETE` means the **verdict** is available: `verdict.verdict`, `risk_score`, `confidence`, `action`, `summary` (at most 50 words) and the specialist `findings` are final. Batch counters and Insights count the scan at this moment.                                                  |
| `report_status` | `PENDING`, `READY`, `FAILED`               | State of the full report in `verdict.report_markdown`. `PENDING`: still being written, `report_markdown` is `""`. `READY`: stored, with the disclaimer at both ends. `FAILED`: it could not be written; `report_error` holds a short reason such as `not enough time`. |

Each `usage` object counts every prompt token in `input_tokens`, cached or not; `cache_read_tokens` and `cache_write_tokens` say how many of them were Bedrock prompt-cache reads and writes, which `cost_usd` prices at the model's prompt-cache read and write rates (`backend/phish_backend/common/pricing.json`, from the AWS Price List API). A `global.` inference profile is priced at the global rate; a geographic profile (`us.`, `eu.`, `apac.`, `au.`, `jp.`) or a bare model id at the in-Region rate. `unpriced_models` lists any model with no price: its tokens are not in `cost_usd`, so the cost is unknown (the UI and the HTML report say so) rather than free, and the worker logs a warning. `total_ms` and `cost_usd` cover the verdict; the report step adds its own cost to `cost_usd` when it finishes, and its call appears in `calls` as a `harness` entry named `report`. `cost_final` (on `GET /scans/{id}`, `GET /history` and `GET /batches/{id}` items) is `true` once nothing will add to `cost_usd`: the scan is `FAILED`, or it is `COMPLETE` and `report_status` is `READY` or `FAILED`. Poll until `cost_final` is `true` if you need the final cost. `cost_usd` stays a decimal string such as `"0.0712"` (not a JSON number), so existing clients keep parsing it the same way. `report_started_at` is when the verdict was stored and the report began. `report_ready_at` is when the report finished, whether it is `READY` or `FAILED` (null while `PENDING`). All three fields are ISO 8601 UTC strings, or null. They appear on `GET /scans/{id}`, `GET /history` and `GET /batches/{id}`.

How to read it:

- Poll `GET /scans/{id}` until `status` is `COMPLETE`, show the verdict, then keep polling while `report_status` is `PENDING`. How long the report takes after the verdict: on the Harness path, in a 50-URL batch on 2026-10-21, it was about 11 s at the median (p50 42.5 s to the verdict, 53.8 s to the report, once the scan was picked up); the report was not timed on its own on the current default, and earlier designs are in [evaluation.md](evaluation.md#latency-history). An HTTP 404 or site-down answer has its report immediately.
- A report that is `FAILED` never changes the verdict. `POST /scans/{id}/retry` still accepts only scans whose `status` is `FAILED`, so a COMPLETE scan with a FAILED report is not re-run by it; submit the URL again if you need the report. Retrying a FAILED scan is unchanged.
- A scan stored before this behaviour has no `report_status` and reads as `READY`.
- The HTML report (`GET /scans/{id}/report`) works as soon as the scan is `COMPLETE`. While the report is `PENDING` it shows the verdict and findings with a "full report is still being written" notice; if it is `FAILED` it shows a failure notice instead. The human-review banner is present in every case.
- Insights: the scan, verdict and latency are counted when `status` becomes `COMPLETE`. The cost and tokens of the report step are added to the same totals when it finishes.

### HTTP 404 and site-down fast paths

The worker calls `precheck_url` on the tools server, which opens the URL once in AgentCore Browser (navigation only, no screenshot). By default the three specialists start at the same time as the pre-check. On the Harness path (`-c directOrchestration=false`) the pre-check runs first, before any model. When the browser refuses the URL, cannot reach it or times out, the tool follows up with one plain HTTP probe (GET, up to 5 redirects, nothing executed). The worker waits at most 22 seconds for the answer.

- If the page answers HTTP 404 the scan finishes at once with no orchestrator call: `verdict.verdict` is `error_404`, `risk_score` 10, `confidence` `high`, `action` `allow`, a one-sentence `summary`, and a short fixed `report_markdown` stating the page returned HTTP 404.
- If the site is down (DNS failure, connection refused or reset, HTTP 410, or a redirect to a host that does not resolve) the scan finishes the same way with `verdict.verdict` `site_down` (shown as "Site down"), `risk_score` 10, `confidence` `high`, `action` `allow`, and a fixed `report_markdown` that lists the addresses tried (defanged, in order) and the reason the probe gave.

In both cases `report_status` is `READY` immediately, `report_markdown` carries the bold human-review disclaimer at both ends, `findings` is empty, `cost_usd` is `0`, and `calls` holds one `browser` entry named `precheck`. On the default path the specialists that already started still finish and their tokens are billed to your account, but the worker never reads their Findings and `cost_usd` does not include them. On the Harness path no specialist runs. Every other outcome (page reachable, unreachable, blocked, or a precheck that failed or timed out) runs the normal analysis; a precheck problem never fails a scan. The worker calls the tools runtime directly for the pre-check; every deployment has it, and the fast paths are skipped only if `TOOLS_RUNTIME_ARN` is not set on the worker. `site_down` counts in batch `verdict_counts`, the `/stats` totals and daily series, and the CSV export like any other verdict.

### Signals, capture notes and code insights

Each Finding has `signals`, each with a `name`, `severity` and `evidence`. Names come from a fixed catalog where the code emits them (for example `blocked_by_browser`, `telegram_bot_exfil`); models mostly reuse catalog names. The catalog (`contracts/phish_contracts/signal_catalog.json`, copied to `web/src/lib/signalCatalog.json`) maps a name to a short `title` and a plain `explain` sentence; an unknown name is shown humanized (`brand_in_subdomain` as "Brand in subdomain"). `blocked_by_browser`, `bot_challenge`, `tls_error` (the site answered but its certificate or TLS setup was rejected; the site is not down) and `static_html_only` (the browser could not load the page, so `code_analyst` read only its raw HTML, not rendered and scripts not run) are capture gaps (the page could not be fully seen), never evidence of phishing on their own.

Two optional Finding fields are written by code, never by a model, and are null on older scans:

- `capture_note`: one plain sentence on how the capture went, for example "A bot check was shown instead of the page, so its content was not captured."
- `redirect_chain` (at most 10 hops): how the scan got from the submitted URL to the page judged. `brand_visual` and `code_analyst` record the browser's hops, `url_analyst` the URL's HTTP redirects. Each hop has `url` (exact, a machine field: defang it before showing it), `via` (`start`, `http` for a 3xx, `client` for a script or meta refresh navigation, `warning_bypass` for the one click past a provider warning), `status` (or null), `error` (a `net::ERR_*` code or probe reason when the hop did not load, or null) and the flags `cross_domain` (moved to another site), `free_hosting` and `shortener`. Empty on older scans and on one-hop chains from older agents.
- `page_observed` (`brand_visual` and `code_analyst`): `true` when the capture saw the site's real page, `false` when a provider warning, bot check, block page or failed capture stood in front of it.
- `insights` (`code_analyst` only): what the page's code does. `endpoints` (up to 20, off-domain first) each with a defanged `url`, `kind` (`fetch`, `xhr`, `beacon`, `form`, `websocket`, `image`), and `off_domain`; `forms` (up to 10) each with a defanged `action` (`""` when none), `fields` (input types in order) and `submits_via_js`; `script_count`, `script_kb`, and `external_script_hosts` (up to 15 registered domains, http and https sources only). Capture is passive and never types into a page.

`verdict.page_observed` is written by the worker, never by the model: `false` when no browser capture saw the real page, `true` when one did, absent on fast-path and older scans. When it is `false` and a `cloudflare_phishing_warning`, `cloudflare_malware_warning` or `www_sibling_capture` signal is present, the verdict is at most `suspicious` with `risk_score` at most 69 and `action` `warn`, `summary` starts with "Page not observed:", and `report_markdown` starts with a "Page not observed" note. New signal names: `warning_bypass_blocked` (the browser could not get past a provider warning; a capture gap), `redirect_to_free_hosting`, and, since 2026-10-26, `static_html_only` (a capture gap; `page_observed` stays `false`). `www_sibling_capture` (since 2026-10-27): the certificate does not cover the submitted `www.` name, so the same site without `www.` was captured instead; it comes with the `tls_error` signal and `page_observed` stays `false`.

`verdict.capped_from` appears only when that cap changed the answer: it holds the model's own `verdict`, `risk_score` and `action` before the cap, so you can see what was held back. The worker sets it; a value written by the model is ignored.

## Use it as a pre-publish gate

A publish flow can call `POST /scan`, poll `GET /scans/{id}` until `status` is `COMPLETE` or `FAILED` (no need to wait for the report), and decide from the verdict:

| The scan says | What the gate does |
| --- | --- |
| `status` `FAILED` | Hold the link and send it to human review |
| `verdict.action` `block`, or `verdict.risk_score` at or above your threshold (70 in the README example) | Hold the link and send it to human review |
| `verdict.action` `warn` (Suspicious or Unknown) | Send it to human review |
| `verdict.page_observed` is `false` | Send it to human review: a provider warning, bot check or failed capture hid the real page. Behind an unpassed provider warning the verdict is capped at `suspicious`, risk 69, so a risk threshold alone lets it through |
| `verdict.action` `allow` and `page_observed` is not `false` | Publish |

> [!WARNING]
> The verdict is advisory. Hold risky links for a person to review rather than rejecting them automatically. A complete gate script is in the [getting started guide](getting-started.md#test-the-api-a-pre-publish-gate).

## The disclaimer field

Every JSON response has a top-level string field `disclaimer` holding the sentence "This output was generated by AI and can be wrong. A qualified human analyst must review it before any action is taken." This includes errors, whether the Lambda function built them (for example `404 scan not found`) or API Gateway did before the function ran: a malformed or schema-invalid request body (`400`), a request without valid SigV4 credentials (`403`), an unknown route (also `403`, `Missing Authentication Token`, because the API is IAM-authorized), a throttled request (`429`) and a gateway failure (`5xx`). Every error, from the Lambda function or from API Gateway, uses one envelope, `{"error": "<message>", "disclaimer": "..."}`, for example `{"error": "Invalid request body", "disclaimer": "..."}`, and keeps its status code. Branch on the status code (and, for API Gateway errors, the `x-amzn-ErrorType` header), not on the text. A bad or expired SigV4 signature gets a fixed message ("The request signature does not match. Sign the request with SigV4 for service execute-api and the exact method, path, query and body sent." or "The security token included in the request has expired."), never the canonical request. The only exception is `GET /health`. Existing fields are unchanged, so a client that ignores unknown keys keeps working; a client that compares a whole body for equality should ignore `disclaimer`.

Records are scoped to the caller: you only ever see your own scans and batches, and no response body returns an identity (no `owner` field, no account id or role name).

## Scan up to 50 URLs in one request

```bash
awscurl --service execute-api --region "$AWS_REGION" -X POST "$API/batches" \
  -H 'Content-Type: application/json' \
  -d '{"urls": ["https://example.com", "https://example.org"]}'
# {"batch_id": "b7c0...", ...}

awscurl --service execute-api --region "$AWS_REGION" "$API/batches/b7c0..."
```

`GET /batches/{id}` returns the batch record under `batch` (counts, cost, and the upload lifecycle: `awaiting_upload`, `split_at`, `error`), then `invalid_rows`, `error`, `p50_ms`, `p95_ms` with `p50_over_max`, `p95_over_max`, `p50_bound`, `p95_bound`, and one page of the batch's scans under `items` (`?limit=` up to 200; pass the returned `next` as `?next=` for the following page) beside it. The percentiles are exact when that first page holds every timed scan of the batch; otherwise they come from the batch's latency buckets, are bucket upper edges, and carry `*_bound: true`. A batch with an `error` is closed: `completed_at` is set and it will not progress.

## Scan up to 1,000 URLs from a CSV

1. Ask for an upload slot:

   ```bash
   awscurl --service execute-api --region "$AWS_REGION" -X POST "$API/batches" \
     -H 'Content-Type: application/json' -d '{"upload": true, "count": 1000, "source": "api"}' > slot.json
   ```

2. Upload the file to the presigned POST (fields first, file last; the slot expires in 15 minutes):

   ```bash
   args=(); while IFS= read -r kv; do args+=(-F "$kv"); done < <(jq -r '.upload_fields | to_entries[] | "\(.key)=\(.value)"' slot.json)
   curl -sS "${args[@]}" -F "file=@urls.csv" "$(jq -r .upload_url slot.json)"
   ```

3. Poll `GET /batches/{id}` with the `batch_id` from `slot.json`.

CSV rules: a header row is optional, CRLF or LF line endings both work, the first column is the URL, blank lines and duplicates are dropped, invalid rows are listed in `invalid_rows`. The file can be up to 1 MB.

## Python example

```python
"""Scan one URL through the API and print the verdict. Needs boto3."""

import json
import os
import time
import urllib.request

import boto3
from botocore.auth import SigV4Auth
from botocore.awsrequest import AWSRequest

API = os.environ["API"]
REGION = os.environ["AWS_REGION"]
credentials = boto3.Session(region_name=REGION).get_credentials()


def call(method: str, path: str, body: dict | None = None) -> dict:
    data = json.dumps(body).encode() if body is not None else None
    request = AWSRequest(
        method=method, url=API + path, data=data, headers={"Content-Type": "application/json"}
    )
    SigV4Auth(credentials, "execute-api", REGION).add_auth(request)
    prepared = urllib.request.Request(
        API + path, data=data, method=method, headers=dict(request.headers)
    )
    with urllib.request.urlopen(prepared, timeout=30) as response:  # nosec B310: fixed https API URL
        return json.load(response)


scan = call("POST", "/scan", {"url": "https://example.com"})
while (result := call("GET", f"/scans/{scan['scan_id']}"))["status"] not in ("COMPLETE", "FAILED"):
    time.sleep(2)
print(result["status"], (result.get("verdict") or {}).get("verdict"), result.get("error"))
```

## Stats and export

```bash
awscurl --service execute-api --region "$AWS_REGION" "$API/stats?range=7d"
awscurl --service execute-api --region "$AWS_REGION" "$API/stats/export?range=30d" > scans.csv
```

`GET /stats` returns `totals` (`scanned`, `phishing`, `suspicious`, `legitimate`, `unknown`, `error_404`, `site_down`, `failed`, `cost_usd`, `unpriced_scans`, `input_tokens`, `output_tokens`, `avg_ms`, `p95_ms`, `p95_over_max`, `p95_bound`), `daily`, `latency_histogram`, `by_model` (each with `cost_known`, false when some of that model's calls had no price), `agentcore` and `recent_batches`. `cost_usd` is a decimal string. `p95_ms` comes from latency buckets, so it is normally a bucket upper edge: `p95_bound: true` marks it as an upper bound and `p95_over_max: true` means it fell in the top bucket (the reported value is the finite top edge, not the true latency). A single timed sample reports its exact duration with both flags false. Each `agentcore` entry is one call kind and name with `kind`, `name`, `count`, `avg_ms`, `p95_ms`, `p95_over_max`, `p95_bound`, `errors` and `blocked` (calls stopped by a guardrail). Ranges: `24h`, `7d`, `30d`, `all`. You see only your own scans.

The export CSV has these columns:

```text
scan_id,batch_id,url_defanged,status,verdict,risk_score,queued_at,completed_at,total_ms,input_tokens,output_tokens,cost_usd,disclaimer
```

`disclaimer` is the last column and holds the same sentence on every row. It is a column rather than a comment or title line so the file stays plain CSV that any parser, spreadsheet or `csv.DictReader` reads unchanged, and so the notice survives filtering and sorting. An export with no scans has only the header row.

## HTML reports

```bash
awscurl --service execute-api --region "$AWS_REGION" "$API/scans/$SCAN_ID/report"
awscurl --service execute-api --region "$AWS_REGION" "$API/batches/$BATCH_ID/report"
# {"url": "https://...amazonaws.com/scans/.../report.html?X-Amz-...", "expires_in": 900}
```

Each call renders the report from the stored records, writes it to the artifacts bucket (`scans/{id}/report.html` or `batches/{id}/report.html`, expired with the other artifacts after 30 days) and returns a presigned link that downloads it for 15 minutes. The scan report holds the orchestrator verdict and report, a section per specialist (verdict, confidence, latency, signals shown by catalog title and explanation, the capture note, and for the code analyst a compact table of the code insights), timings, and token use and cost. Both reports open with a bold human-review banner and repeat it in the footer. The batch report is a table of every scan in the batch: defanged URL, status, verdict, risk, confidence, cost and a link to the scan in the web console. Every value is HTML-escaped, URLs are defanged, and a Content-Security-Policy blocks scripts and every external load. A scan report for a scan that is not COMPLETE answers `409`. The full-report section follows `report_status`, see [Verdict first, report second](#verdict-first-report-second).

| `GET /batches/{id}/report`        | Link to the batch's HTML report                                | IAM  |
| `POST /batches/{id}/retry-failed` | Run every FAILED scan in the batch again                       | IAM  |

## Errors and limits

| Status | Meaning                                                                                                                                   |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `400`  | The request is invalid: a malformed URL, an unknown body field or a `force` that is not a boolean, a malformed `Idempotency-Key`, more than 50 URLs in a JSON batch, a `count` or `source` out of range, or a bad `limit`, `range` or `include_failed`. The body says why. |
| `403`  | The request is not signed, or the signer may not call the API.                                                                            |
| `404`  | No such scan or batch, or it belongs to someone else.                                                                                     |
| `409`  | You retried a scan that is not FAILED, asked for the report of a scan that is not COMPLETE, or sent an `Idempotency-Key` whose first request is still being processed (honor `Retry-After`). |
| `422`  | The `Idempotency-Key` was already used with a different `url`.                                                                            |
| `501`  | `Idempotency-Key` sent to a custom deployment without the idempotency table. The stack in this repository always creates the table, so a default deploy never answers `501`. Retry without the header. |
| `429`  | Throttled. The request did not run. Retry with exponential backoff and jitter, and honor `Retry-After` if it is present.                 |
| `503`  | A new scan or a retry could not be queued, or the live feed is unavailable. Try again later (with the same `Idempotency-Key`, if you sent one). |

Limits: 200 URLs per upload in the web app, 1,000 per CSV through the API, 50 per JSON request, 25 scans running at once per deployment. The API stage allows 50 requests per second with bursts of 100.

## Retries and scan completion

No scan is dropped. Every URL you submit ends `COMPLETE` or `FAILED`, and a FAILED scan always has a reason in `error`. The service retries transient errors itself (3 attempts) before it marks a scan FAILED. A single `POST /scan` whose queue send fails twice is answered `503` and stored as `FAILED`; for batches, every 5 minutes the service re-queues scans stuck in `PENDING`, and marks a CSV batch whose file was never uploaded as `FAILED` with the reason "CSV was never uploaded".

Retry one scan, or every FAILED scan in a batch:

```bash
awscurl --service execute-api --region "$AWS_REGION" -X POST "$API/scans/3f2a9c1e-7b4d-4e0a-9d61-0c8e5b2f7a10/retry"
awscurl --service execute-api --region "$AWS_REGION" -X POST "$API/batches/b7c0.../retry-failed"
# {"batch_id": "b7c0...", "retried": 2}
```

Amazon Bedrock Guardrails check every submitted URL and every report. An intervention is listed in `guardrail_events` and never stops a scan.
