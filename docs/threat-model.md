# Threat model

This page lists what can go wrong, what the sample does about it, and what risk is left for you to accept. Controls are described in [security.md](security.md).

## System

Signed-in users submit URLs in a web app or through a SigV4-signed API. Each URL is queued and analysed by an orchestrator agent. By default (the latency flags, see [configuration.md](configuration.md)) the worker invokes the three specialists directly and asks the orchestrator model for the verdict and report through Amazon Bedrock, and the capturing specialists call their own tools runtime copies directly. With `-c directOrchestration=false` or `-c agentRegistry=true` the orchestrator runs on AgentCore Harness, which reaches three specialist agents on AgentCore Runtime through AgentCore Gateway: it calls one dispatcher tool, whose no-model runtime runs the three specialists concurrently, and may call one specialist tool once more in a second round (with `-c agentRegistry=true` it first looks the specialists up in AWS Agent Registry, part of Amazon Bedrock AgentCore, through a `registry` target on the same Gateway); the specialists call one shared tools server through a second Gateway, which opens the URL in AgentCore Browser (signed with Web Bot Auth only with `-c browserSigning=true`), and the worker first calls the same tools server directly for a pre-check that answers HTTP 404 and dead sites without a model. The orchestrator answers in two turns: the verdict is stored first and the report afterwards. Specialists share a small DynamoDB result cache of public-source lookups. Results, timings and cost are stored per user in DynamoDB and S3. See the [architecture diagram](architecture.png).

## Trust boundaries

| #   | From                               | To                           | Control at the boundary                                   |
| --- | ---------------------------------- | ---------------------------- | --------------------------------------------------------- |
| B1  | Browser                            | CloudFront                   | TLS, AWS WAF, rate limit                                  |
| B2  | CloudFront                         | Web Lambda and web S3 bucket | Origin access control; the Function URL requires IAM auth |
| B3  | Web Lambda                         | Cognito                      | Cognito authentication; session cookie                    |
| B4  | Caller (web tier or IAM principal) | API Gateway                  | SigV4 (IAM auth), stage throttling                        |
| B5  | Lambdas                            | DynamoDB, S3, SQS            | One IAM role per function, KMS                            |
| B6  | Worker Lambda                      | AgentCore Harness (Harness path, `-c directOrchestration=false`) | IAM on one harness ARN                                    |
| B19 | Worker Lambda (default path) | Specialist runtimes (the dispatcher runtime with `-c directSpecialists=false`) | IAM: `InvokeAgentRuntime` on the three specialist runtimes and their endpoints (or on the dispatcher runtime), never on a tools runtime beyond B15; each specialist validates the scan id and writes only its own Finding; the worker cannot write Findings |
| B20 | Worker Lambda (default path) | Amazon Bedrock | IAM on the orchestrator inference profile only (Converse, verdict and report turns); the Findings are sent labelled as untrusted data; the output guardrail screens the report |
| B7  | Harness                            | AgentCore Gateway            | AWS_IAM authorizer                                        |
| B8 | Gateway `phish-specialists` | Dispatcher and specialist runtimes; Agent Registry with `-c agentRegistry=true` | IAM: the Gateway invokes the dispatcher and the three specialist runtimes as MCP targets (four runtime ARNs and their endpoints, not the tools runtime). Only with `-c agentRegistry=true` it also serves a `registry` target that searches the stack's own Agent Registry records. Records are stack-owned and auto-approved |
| B18 | Dispatcher runtime | Specialist runtimes, S3 findings | IAM: `InvokeAgentRuntime` on the three specialist runtimes and their endpoints only; `PutObject` on the three `scans/*/findings/<agent>.json` keys only, if absent, for an error Finding; no model, browser, Gateway or cache grant; validates the scan id before any call |
| B9  | Specialists, and the orchestrator harness on the Harness path | Amazon Bedrock | IAM on two inference profiles; Guardrails. The worker's own model calls are B20 |
| B10 | AgentCore Browser                  | Untrusted internet           | Isolated session per URL, SSRF guard on every hop, requests signed with Web Bot Auth when `browserSigning` is on, passive capture |
| B17 | HTTP probe: pre-check and `code_analyst` raw HTML fallback (tools runtime), `url_analyst` redirect read (in process) | Untrusted internet | GET only, at most 5 redirects, the SSRF guard on every hop and the connection pinned to the address it approved, 64 KB read on the wire with no decompression and 8 s caps; the probe never parses or executes content. For `code_analyst` an uncompressed HTML body is tokenized by `html.parser` (never executed or rendered, nothing it links to fetched) into a bounded excerpt that the model reads as untrusted content (T2) |
| B11 | RDAP lookup                        | RDAP servers                 | HTTPS only, SSRF guard on every redirect                  |
| B12 | brand_visual runtime | Web search Gateway (us-east-1; in a Region that offers Web Search, its own regional Gateway), then AgentCore Web Search | SigV4, AWS_IAM authorizer, InvokeGateway on one gateway ARN; the Gateway role may invoke only the AWS-owned web search tool |
| B13 | Specialist runtimes (only with `-c directTools=false`, on either path) | Tools Gateway, then the tools runtime | SigV4, AWS_IAM authorizer, InvokeGateway on one gateway ARN held by the three specialist roles only; the harness cannot reach it; the tools re-validate URL and scan id |
| B21 | brand_visual and code_analyst runtimes (default path, `directTools`) | Their own tools runtime copy | IAM: `InvokeAgentRuntime` on that one copy and its endpoints only (the shared tools runtime with `-c splitToolsRuntimes=false`); no Gateway, so the tools re-validate URL and scan id themselves; url_analyst holds no tools runtime grant and runs RDAP in process |
| B15 | Worker Lambda | Tools runtime | IAM: `InvokeAgentRuntime` on the tools runtime and its endpoints only, for `precheck_url`, on both paths. The call skips the Gateways, so the tools re-validate URL and scan id themselves. On the Harness path the worker holds no grant on a specialist; on the default path see B19 |
| B16 | url_analyst, brand_visual and tools runtimes | DynamoDB result cache (`phish-cache-{env}`) | IAM `GetItem`, `PutItem`, `UpdateItem` by key on that one table plus the data CMK; no Query, Scan or Delete; no scan content is stored; failures fail open to a live lookup. The orchestrator and the worker hold no grant |

## Threats and mitigations

| ID  | Threat                                                                    | Mitigation                                                                                                                                                          |
| --- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T1  | One user reads another's scans, batches, stats or export (IDOR)           | Owner check on every read, `404` otherwise; stats keyed by owner                                                                                                    |
| T2  | Prompt injection in the URL, page content (including the raw HTML excerpt `code_analyst` reads when the browser cannot load the page) or web search results | Untrusted-content framing and size caps (the raw HTML excerpt is fenced as "raw HTML excerpt, not rendered, scripts not run", bounded per field and to 30,000 characters, with code-derived signals first so padding cannot push them out; in that mode code forces a `legitimate` verdict to `unknown`, since a kit can serve clean HTML to a plain GET); tools take no URL argument; the web search tool takes only a sanitized brand name and marks results from the scanned site; output schema validation; verdict parsed from the last `<verdict>` block, or with none from the last JSON object with a `verdict` key |
| T3  | Batch amplification drives cost or load                                   | Caps: 200 (UI), 1,000 (API CSV), 50 (JSON); SQS with 25 in flight; WAF rate limit; API throttling                                                                   |
| T4  | Data exfiltration from stored results                                     | KMS on every store, Block Public Access, least-privilege roles, owner isolation                                                                                     |
| T5  | Wrong or harmful verdict                                                  | Confidence and evidence shown with every verdict; a person decides; a bold human-review disclaimer in every JSON response (`disclaimer`), HTML report, CSV row and the end of the orchestrator report, appended by the service, not the model; see [responsible-ai.md](responsible-ai.md) |
| T6  | The global inference profile routes specialist requests outside the US    | Accepted for this sample. Set `-c specialistModel=` to a `us.` profile to keep data in the US                                                                       |
| T7  | Unauthenticated API access                                                | IAM SigV4 on every route except `/health`; Cognito gates only the web console, never the API. Call it with your AWS CLI credentials (`awscurl`), see [api.md](api.md#authentication) |
| T8  | A hostile page attacks the agent or its browser                           | AgentCore Browser sandbox, one session per URL, always closed, no credentials in the session; page code never runs elsewhere                                        |
| T9  | Log injection through URLs                                                | Structured JSON logging; URL validation before logging                                                                                                              |
| T10 | Dependency supply chain                                                   | Pinned lock files; dependency and code scanners before each push                                                                                                    |
| T11 | Invite code brute force on `POST /auth/register` (when `inviteCode=true`) | Secrets Manager generates a 32-character code, so guessing is infeasible; constant-time comparison; the same `403` for every wrong code; WAF rate limit |
| T12 | Account enumeration through register or sign-in | Register returns the identical response whether or not the account exists; sign-in reveals nothing (Cognito prevent user existence errors) |
| T13 | Direct call to the web Function URL, bypassing WAF                        | Function URL requires IAM auth; only CloudFront (origin access control) can sign                                                                                    |
| T15 | Unauthenticated user receives the app shell to probe                      | The web tier serves the app only to signed-in users, except sign-in, register and the post-register welcome page                                                   |
| T23 | Register used to send mail to addresses the caller does not own (email bombing) or to exhaust the 50 emails per day default | WAF limit of 10 `POST /auth/register` per 5 minutes per IP (`429`); optional invite code and domain allowlist; identical response; `-c sesFromAddress` for SES sending limits and monitoring |
| T16 | Session cookie theft or misuse                                            | `Secure`, `HttpOnly`, `SameSite` cookie with a short lifetime                                                                                                       |
| T17 | Open registration lets anyone spend Bedrock tokens | No per-user quota (decision 2026-09-29, accepted). A new account needs the temporary password emailed to its address, so it proves inbox ownership; WAF rate limit, optional invite code and email domain allowlist |
| T18 | Presigned upload abuse                                                    | 1 MB cap, `text/csv` only, key scoped to owner and batch id, 15-minute expiry, 1-day lifecycle                                                                      |
| T19 | Page content makes the orchestrator call a tool for another scan id       | Tools accept only `url` and `scan_id`; the worker owns scan ids; specialists write only under their scan prefix                                                     |
| T20 | SSRF through the RDAP lookup, browser navigation or the HTTP probe        | SSRF guard on every request and redirect: the host is resolved and refused when any address is internal (decisions cached per origin for 60 s). The HTTP probe resolves each hop uncached and connects only to the approved addresses, so DNS rebinding between check and connect cannot reach an internal address through it; AgentCore Browser and the RDAP client resolve names themselves, so for them the check and the connect are separate lookups. Outbound only through AgentCore Browser, the HTTP probe and the RDAP lookup |
| T21 | WAF body rules in Count on the scan routes                                | Needed so a phishing URL in a body never blocks a scan. Compensated by IAM auth, URL validation, SSRF guard and input guardrail; full blocking on every other route |
| T24 | Episodic memory reveals one user's scans to another | Memory summaries are shared within a deployment as model context only: the orchestrator may see a summary from any user's scan (defanged URL, verdict, risk, reason; never an owner id or email). The API lists as similar past scans only matches whose scan is owned by the requester, looked up in the `scans` table, and never returns another owner's scan id. `-c episodicMemory=false` turns memory off |
| T28 | One user's scan context reaches another user's scan through the orchestrator harness (tenant isolation) | The harness runs without managed memory. The two turns of one scan share one runtime session, and the worker passes `actorId` = the scan id, so no harness state is shared across scans. Before this change every scan used the harness memory actor `default`, and a 2026-10-16 test showed one session quoting scan ids from earlier sessions. The app's own episodic memory is separate and owner-filtered (T24) |
| T29 | A tampered Agent Registry record steers the orchestrator (`-c agentRegistry=true` only) | Records are stack-owned and auto-approved. The orchestrator can call tools only on its one Gateway, `phish-specialists`, so a tampered record can at most change which of that Gateway's own tools the model picks, never redirect it to another endpoint; round one is always the dispatcher call. If the lookup fails, the orchestrator notes it and goes on |
| T25 | A poisoned RDAP or web search result is cached and served to later scans | The cache holds only public-source lookup results, never scan content; web search results live 24 hours (`webSearchCacheTtlHours`), RDAP 7 days; only successful non-empty answers are stored; cached search text is re-fenced as untrusted and re-marked against each scan's host on every read; the table is readable and writable only by key and only by the url_analyst, brand_visual and tools runtime roles; any cache error falls back to a live lookup. Details in [security.md](security.md#network) |
| T26 | A capture gap is read as phishing evidence (a browser refusal, a bot check or a certificate error on a legitimate or dead site) | `blocked_by_browser`, `bot_challenge` and `tls_error` are `low` capture-gap signals; a certificate error is never `site_down` (the host answered); the orchestrator prompt says capture gaps lower confidence and are never evidence on their own; the pre-check answers dead sites as `site_down` with no orchestrator call (by default the specialists start alongside the pre-check and are billed, but their Findings are never read; on the Harness path no model runs) |
| T27 | The capture tool acts on a hostile page (clicks through a warning, solves a bot check, submits data) | Capture is passive apart from one click: on a Cloudflare warning page, the warning's own same-origin proceed control, only once and only when Cloudflare has enabled it (the Turnstile widget is never touched); no solving bot checks, no typing or submitting data on the site; the HTTP probe only reads; every hop, including those after the click, passes the SSRF guard |
| T22 | A scan is silently lost between queue and result | 3 worker attempts; dead-letter sweeper marks exhausted messages FAILED with a reason; a 5-minute sweep re-queues stuck PENDING scans and fails never-uploaded CSV batches; alarms; user retry |

Removed from the previous version: T14 (identity provider sign-up turned on by accident) is replaced by T17, because Cognito self sign-up is now a supported option (`signUpMode=cognito`) rather than a misconfiguration.

## Residual risks

| Risk                                                             | Rating | Decision                                         |
| ---------------------------------------------------------------- | ------ | ------------------------------------------------ |
| Prompt injection from page content changes a verdict             | High   | Accepted with the T2 controls                    |
| Global inference routing sends specialist traffic outside the US | Medium | Accepted; configurable (T6)                      |
| Signed-in users can spend tokens without a quota                 | Medium | By design (T17)                                  |
| No separate development and production accounts                  | Medium | Sample code; use separate accounts in production |
| Access-log destination bucket has no access logging of its own   | Low    | Accepted; logging it would recurse               |
| Memory summaries of one user's scans reach the model for another user's scan | Low | Accepted as model context only (T24); never shown to another user; opt out with `-c episodicMemory=false` |
| A phishing page behind a provider warning the browser cannot pass is held at Suspicious (risk at most 69) | Low | Accepted: the real page was not seen. Gates route `warn` and `page_observed: false` to human review (T27) |
| A phishing page on a `www.` name its certificate does not cover is held at Suspicious (risk at most 69), even when the same site without `www.` was captured and looks like phishing | Low | Accepted: the submitted page was not seen (visitors get a certificate warning). The sibling host is derived from the submitted URL and passes the same preflight and URL guard. Gates route `warn` and `page_observed: false` to human review (T27) |

## Data classification

| Data                                    | Class (AWS data classification) | Stored in                      | Retention                                       |
| --------------------------------------- | ------------------------------- | ------------------------------ | ----------------------------------------------- |
| Submitted URLs                          | Confidential                    | DynamoDB `scans`, SQS          | `retentionDays` (default 90)                    |
| Verdicts, reports, findings             | Confidential                    | DynamoDB `scans`, S3 artifacts | 90 days; artifacts 30 days                      |
| Scan summaries (episodic memory)        | Confidential                    | AgentCore Memory               | Until the stack is deleted                      |
| Screenshots and page captures           | Confidential                    | S3 artifacts                   | 30 days                                         |
| Job metadata (batches, timings, cost)   | Internal                        | DynamoDB `batches`, `stats`    | 90 days; daily stats until the stack is deleted |
| Owner identity (Cognito sub or IAM ARN) | Confidential                    | DynamoDB                       | With the row it is on                           |
| Email address                           | Confidential (personal data)    | Cognito user pool              | Until the user or pool is deleted               |
| Invite code (optional)                  | Restricted                      | Secrets Manager                | Until the stack is deleted                      |
| Session cookie                          | Restricted                      | User's browser                 | Session lifetime                                |
| Logs                                    | Internal                        | CloudWatch Logs                | Log group retention                             |
| KMS keys                                | Restricted                      | AWS KMS                        | Deleted with the stack (pending window)         |
